## D-001 — React Native flavor: bare React Native Community CLI

**Date:** 2026-10-03 · **Status:** Accepted · **Owner:** A0 · **Blocks:** all agents

### Decision
Use **bare React Native** (React Native Community CLI, `@react-native-community/cli`), scaffolded into `app/`, **not** Expo (neither Expo Go nor Expo prebuild/dev-client). The app is one shared TypeScript codebase; BLE peripheral/advertising and platform crypto are implemented as first-party native modules under A4/A5's direct ownership of `app/ios/**` and `app/android/**`.

### Reasons (grounded)
1. **Hard requirement:** merchant mode needs a BLE **peripheral + advertiser** (iOS `CBPeripheralManager`, Android `BluetoothLeAdvertiser` + GATT server) and platform crypto (CryptoKit / Keystore). Expo Go cannot load custom native code at all — only native libraries bundled in the Expo SDK are available ([Expo: customizing](https://docs.expo.dev/workflow/customizing), "Using Expo Go?").
2. **No CNG round-trip:** the plan gives A4 ownership of `app/ios/**` and A5 ownership of `app/android/**`. With Expo Continuous Native Generation those directories are regenerated by `npx expo prebuild`, so direct native edits would have to be expressed as config plugins/local Expo modules instead ([Expo: Add custom native code](https://docs.expo.dev/workflow/customizing/#considerations-when-using-continuous-native-generation)). That is a second, unneeded convention on top of the native-module work.
3. **Expo prebuild is functionally capable but adds a constraint:** `npx create-expo-module --local` + `npx expo run` does support custom native modules ([Expo: customizing](https://docs.expo.dev/workflow/customizing)), so it is a viable *alternative*, rejected for the ownership/CNG reason above — not for capability.
4. **RN core requirement is unchanged:** even with Expo, BLE peripheral still needs a custom native module; the PoC gains nothing from the Expo toolchain while taking on its native-project regeneration model.

### Alternatives rejected
| Alternative | Verdict | Reason |
|---|---|---|
| Expo Go | Rejected | Cannot run custom native code; no BLE peripheral/advertising, no first-party crypto (docs above). |
| Expo prebuild + dev client | Rejected (viable fallback) | Supports native modules, but CNG owns the native projects, conflicting with A4/A5 direct ownership of `app/ios/**` / `app/android/**`. |
| Separate SwiftUI + Android apps | Rejected | Violates the non-negotiable invariant: ONE shared RN/TS app for both platforms. |
| Flutter / other | Out of scope | Spec/plan mandate React Native. |

## D-002 — Spec boundary: STABLE vs PROVISIONAL

Copied from `DESIGN.md` §13/§14 and `Deceipt_Subagent_Delegation_Plan.md` §0. **Stable items are implemented as written and not re-litigated. Provisional items are finalized by their owner, not assumed.**

### STABLE (§13, §4.4) — implement as written
1. Receipt format is transport-independent. (§13.1)
2. BLE is an untrusted transport. (§13.2)
3. BLE payload is encrypted for privacy. (§13.3)
4. Successful BLE-session decryption does **not** establish receipt trust. (§13.4)
5. Receipt authenticity is independently verified from merchant cryptographic evidence. (§13.5)
6. Long-lived receipt signing keys and ephemeral transport keys are distinct. (§13.6)
7. RSSI cannot select or authenticate a cashier/session. (§13.7)
8. The receiver fails closed when peer association is ambiguous. (§13.8)
9. Exact signed receipt bytes are authoritative. (§13.9)
10. Cryptographic and protocol suites are versioned. (§13.10)
11. Parser and allocation bounds are part of the security design, not polish. (§13.11)
12. Ed25519 receipt signatures, carried as COSE `EdDSA`. (§4.4)
13. iOS key storage: CryptoKit `Curve25519.Signing.PrivateKey`, private material in Keychain; **no** Secure Enclave claim. (§4.4)
14. Android: direct Keystore Ed25519 if supported, else app-generated key wrapped by a device-bound Keystore AES key — explicitly **not** hardware-backed non-exportable. (§4.4)
15. Receipt identity: random, globally unique receipt ID; used for dedup/idempotency. (§4.5)
16. Verification order fixed at 16 steps, with **no failure path reaching "verified"**. (§9)
17. Threat model: 9 named adversaries + mitigations. (§10)

### PROVISIONAL (§14) — must be finalized, not assumed
- deterministic CBOR as receipt/control encoding (§4.2, tentative);
- COSE_Sign1 as the signed receipt container (§4.3, tentative);
- transfer session suite: P-256 ECDH + HKDF-SHA-256 + AES-256-GCM + SHA-256 transcript (§6.2, tentative);
- exact key schedule, directional keys, nonce construction, transcript canonicalization, replay window (§6.4 — "do not improvise during implementation");
- merchant device credential format and PoC trust-bootstrap rule (§5.1–§5.2);
- three-characteristic GATT layout; **all UUIDs are unassigned** (§7.4);
- candidate-ambiguity disambiguation path in production (§7.3 gives the PoC rule only);
- revocation model; historical timestamp/anti-backdating model (§5.4, out of scope for the PoC);
- production hardware-backed merchant signing-key policy and future migration;
- Deceipt as sole PoC trust root; merchant enrollment/identity proofing; merchant-owned delegation roots.

`DESIGN.md` §15 prescribes four design passes before implementation: **A** receipt schema, **B** trust hierarchy, **C** handshake byte-for-byte, **D** UUIDs/wire identifiers. These are A1's gate, not a preamble to skip.

### Non-negotiable invariants (violation ⇒ output rejected)
1. ONE shared RN/TypeScript app for iOS + Android (merchant + customer modes). No separate SwiftUI or Android UI app.
2. BLE is an untrusted transport; AEAD decryption success ≠ trusted receipt.
3. Trust requires merchant signature over the **exact received bytes** + merchant-key authorization. Never re-encode-then-verify.
4. Long-lived merchant signing keys are never reused for session key agreement.
5. RSSI is never a selection, association, or trust signal.
6. Ambiguous peer association fails closed.
7. Parser/allocation bounds are security requirements, not polish.
8. Merchant private keys and session secrets never enter committed files, ordinary logs, or JS bridge payloads.

## D-003 — Root layout and ownership

`git init` at project root; the RN app lives in `app/`; the shared native bridge types live at `app/src/native/DeceiptNative.ts` (drafted by A3, implemented identically by A4/A5); native module sources live in `modules/deceipt-native/{ios,android}/`; protocol artifacts live in `protocol/{schema,vectors,flows}/` and `docs/{protocol,flows,status}/`. Ownership scopes are exclusive per `Deceipt_Subagent_Delegation_Plan.md` §1.

Root config (`package.json`, `tsconfig.json`, `app.json`, `metro.config.js`, `Podfile`, root Gradle wiring) is owned by A0. A4/A5 route root config changes through A0.

**Branch strategy (deviation from plan §2.3, recorded):** the plan proposed one git worktree/branch per agent. By the time the baseline landed, A1 and A2 were already dispatched and writing in the shared tree, and both had landed commits (e.g. `d09776a`). Converting them to worktrees mid-flight would break their working directories and force a rebase of in-progress work for no isolation benefit, since the §1 ownership scopes are exclusive and disjoint (A1: `protocol/**` + `docs/protocol/**`; A2: `protocol/flows/**` + `docs/flows/**`; A3: `app/src/**` + `app/tests/**`; A4: `app/ios/**` + `modules/deceipt-native/ios/**`; A5: `app/android/**` + `modules/deceipt-native/android/**`; A6: `tests/**` + `docs/security/**` + `docs/demo/**`). Decision: **single shared branch, exclusive path scopes**, with A0 as the only committer of root config. This preserves the plan's isolation intent (no agent can write another's files) without the worktree churn.

**Secrets policy:** merchant private keys and session secrets never enter committed files, ordinary logs, or JS bridge payloads. `.gitignore` excludes key material; `protocol/vectors/**` may hold **test-only deterministic** keys/nonces (explicitly un-ignored for that path).

## D-004 — Email receipt compatibility path

**Date:** 2026-10-03 · **Status:** Accepted · **Scope:** product/backend planning

### Decision
Deceipt will support a compatibility path for merchants that only offer email receipts. A user may provide a Deceipt-managed address such as `<handle>@deceipt.com`; the future Deceipt backend receives the retailer email, parses it, and adds the resulting receipt to the user's account.

### Trust boundary
An email-imported receipt is **not** a native merchant-verified Deceipt receipt. SPF/DKIM/DMARC and sender metadata may be retained as email evidence, but they do not replace the existing merchant-signature + credential verification path.

Email imports therefore preserve a source/trust state equivalent to `source=email`, `verification=external_unverified` unless a future independent Deceipt-verifiable artifact is present.

### Design reference
See `docs/product/email-receipt-ingestion-v1.md`.

## D-005 — Laya/System-One is an enrichment layer, not receipt authority

**Date:** 2026-10-03 · **Status:** Accepted · **Scope:** product/model planning

### Decision
Deceipt will integrate a fast System-One classifier, initially Laya-compatible, for receipt organization: categories, merchant grouping suggestions, tags, personal/business suggestions, line-item categories, routing, and recurring-spend candidates.

System-One runs asynchronously after receipt persistence and is replaceable behind a narrow classifier contract.

### Invariants
- Model failure never blocks receipt capture.
- System-One never establishes merchant trust or signature validity.
- System-One never silently changes canonical totals, taxes, tips, currency, timestamps, or source evidence.
- User overrides take precedence over model output.
- Model/taxonomy versions and confidence are persisted with enrichment.

### Design reference
See `docs/product/system-one-classification-v1.md`.

## D-006 — Insights use deterministic receipt projections

**Date:** 2026-10-03 · **Status:** Accepted · **Scope:** product/analytics planning

### Decision
Add an Insights page for spending habits across supported receipt sources. Displayed spending totals and trends are computed deterministically from stored normalized receipt facts plus effective enrichment. They are not generated by an LLM/System-One model at view time.

### Initial behavior
Insights include spend over time, category and merchant breakdowns, receipt count/average, period comparison, recurring-spend candidates, filters, and drill-down to contributing receipts.

Refunds/voids must follow receipt semantics; incomplete imports may be excluded from monetary aggregates; mixed currencies are not silently summed without an explicit FX policy.

### Design reference
See `docs/product/insights-v1.md`.
